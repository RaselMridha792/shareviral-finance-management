# Deploying

Two hosts, one repository, one domain as far as the browser is concerned.

```
browser  ──►  sfm.vercel.app          Next.js on Vercel
                  │
                  ├─ /            the app
                  └─ /api/*       rewritten, invisibly, to ↓

              sfm-api.onrender.com    NestJS on Render
                  │
                  └──►  Neon PostgreSQL (Singapore)
```

**The rewrite is load-bearing, not decoration.** Both auth tokens are
`sameSite: "lax"` httpOnly cookies, and a browser will not attach those to a
request aimed at a different site — `vercel.app` is on the Public Suffix List,
so two Vercel subdomains genuinely count as different sites. Calling the API on
its own hostname would mean either no cookies at all or `sameSite: "none"`,
which gives away the CSRF protection. One origin keeps both, and it is the same
shape nginx will have on the VPS.

---

## 1. The API, on Render

Create a **Blueprint** from this repository. `render.yaml` at the root describes
the service, so the only manual part is the secrets.

| Setting | Value |
| --- | --- |
| Root directory | `.` — the repo root, **not** `apps/api` |
| Build | `npm ci && npm run build:shared && npm run build:api` |
| Start | `node apps/api/dist/main.js` |
| Health check | `/api/health` |
| Region | Singapore |

Building from the root matters: the API imports `@finance/shared`, which is a
workspace sibling that has to be compiled first. From `apps/api` the workspace
is not visible and the build fails on the import.

Render prompts for these:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | the Neon **pooled** string (the host with `-pooler`) |
| `DATABASE_URL_UNPOOLED` | the Neon direct string |
| `CORS_ORIGINS` | `https://sfm.vercel.app` — your Vercel URL, filled in after step 2 |

`JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are generated by Render. Do not
reuse the development ones.

> On the free plan the service sleeps after 15 minutes idle and takes ~30
> seconds to wake. The first request of the morning will be slow; nothing
> breaks. A paid plan removes it, as does the VPS.

Once it is live, `https://sfm-api.onrender.com/api/health` should answer
`{"status":"ok"}`.

## 2. The web app, on Vercel

Import the same repository.

| Setting | Value |
| --- | --- |
| Root directory | `apps/web` |
| Include files outside root | **on** — it needs `packages/shared` |
| Framework | Next.js (detected) |
| Build command | `cd ../../packages/shared && npm run build && cd ../../apps/web && next build` |

Environment variables:

| Variable | Value | Why |
| --- | --- | --- |
| `API_URL` | `https://sfm-api.onrender.com/api` | Server-side calls and the rewrite target. Absolute, because a Server Component has no origin to be relative to. |
| `NEXT_PUBLIC_API_URL` | `/api` | What the browser uses. Relative on purpose — it goes through the rewrite and stays same-origin. |

Getting these backwards is the one mistake that breaks everything quietly:
point the browser at the Render hostname and sign-in appears to work until the
first page reload, when the cookies are not sent back.

## 3. Wire them together

1. Copy the Vercel URL into Render's `CORS_ORIGINS` and redeploy the API.
2. Create the schema and the first accounts, from your own machine with the
   production `DATABASE_URL` in `apps/api/.env`:

   ```bash
   npm run db:push
   npm run db:seed              # prints the passwords once — copy them now
   npm run db:seed-categories
   ```

3. Sign in, and immediately change the Super Admin password.

## 4. Check it properly

Not "the page loads" — the things that break silently:

```bash
# The API is up and can reach the database
curl https://sfm-api.onrender.com/api/health

# The rewrite works and is same-origin: this must return 401, not 404 and not CORS
curl -i https://sfm.vercel.app/api/auth/me
```

Then in a browser:

- [ ] Sign in, then **reload the page**. Still signed in? If not, the cookie is
      not coming back — check `NEXT_PUBLIC_API_URL` is `/api` and not the
      Render hostname.
- [ ] Leave it 20 minutes, then click something. The access token has expired by
      then; the proxy should renew it invisibly. Being bounced to `/login` means
      the refresh cookie is not reaching the proxy.
- [ ] Sign in as HR. No Payroll or TDS in the sidebar, and
      `https://sfm.vercel.app/api/exports/transactions` returns **403**.
- [ ] Sign in as the CEO. Everything readable, nothing editable.

## Moving to the VPS later

Nothing in the application changes. The pieces that move:

| Now | On the VPS |
| --- | --- |
| Vercel rewrite `/api/*` | an nginx `location /api` block |
| Render's Node process | the same `node apps/api/dist/main.js`, in a container |
| Neon | a Postgres container, or keep Neon |
| Vercel's TLS | a self-signed certificate, since there is no domain |

Only `DATABASE_URL`, `API_URL` and `CORS_ORIGINS` change. That is the whole
point of having kept the standard `pg` driver instead of a serverless one.

Before that switchover: take a `pg_dump`, restore it somewhere else, and sign
in against the restore. A backup nobody has restored is not a backup.
